## 机制判定和限制

预期瓶颈不是预设结论。A需同时看到P队列与D缺少工作；B需看到P闲置和D持续解码；C需区分活跃KV容量不足、P计算速度、路由不均和PP调度预算；D的带宽影响用同一TCP后端比较，不能外推纯PCIe P2P。

当前Llama实现的num_used_tokens=总容量−空闲槽位−可驱逐缓存，是不可回收token数，可能包括传输预分配/受保护token，不直接等于正在运行的Decode KV；kv-audit-samples.csv单列free/evictable/protected，审计通常出现在调度器空闲期。框架kv_transfer_speed/latency只有默认值而未实际更新，不能解释为零成本；D组需依赖实际网络计数和端到端对照，缺少逐请求传输关键路径分解。实时指标每2秒采样，scheduler gauge在更新间隔可能保持旧值；峰值及均值为观测统计，不宣称连续全覆盖。PD保持原MiniLB随机路由，需检查各D池而非仅合计容量。输入来自旧Mooncake trace按哈希重建的合成普通token-ID，再抽取连续片段，长前缀独立，并非原始自然语言正文；方案提出真实文本，本轮实际未满足该项，按固定形状合成负载报告；强制固定输出长度，非语义质量实验。

客户端TPOT=(完成−首token)/(输出数−1)，只对成功且至少2token请求统计。缺失TTFT以>cutoff哨兵显示，不是已知真实延迟。goodput仅计完成且满足联合SLO请求，失败和未完成保留在分母。窗口输出吞吐计流式已接收token，排空分母可短于名义窗口。长输出的窗口完成goodput可能为0，即使窗口内已有输出。

### KV 容量的解释

BF16 KV 按该模型配置计算，每 token 全模型 KV 为 32 层 × 8 KV heads × 128 head dimension × K/V 两份 × 2 bytes = 128 KiB；24,576 token 的 Prefill KV 约 3 GiB/请求。这是逻辑 KV 量，不是对网络接口字节的逐请求测量。

PD 每个 TP1 实例有约 425,302–425,303 token 的全层 KV 池，K/V 各约 25.96 GiB。P、D 池相互独立，D 无法直接占用空闲 P 池。原生 A/B/C 中 PP 每个 rank 的分层 KV 池为 2,011,785 token，K/V 各约 30.70 GiB；TCP D1/D2 中则为 2,046,851 token，K/V 各约 31.23 GiB；四个 rank 对同一请求保存不同层，**不能把四个 token 容量相加**。

以请求最终长度 24,576+4,096=28,672 token 估算，不计保留、碎片等开销，PD 每 D 池最多容纳 floor(425303/28672)=14 条完整长度请求，两个池合计约 28 条；PP 由最小 rank 池限制，约 floor(2011785/28672)=70 条。这只是固定最终长度的 KV 容量上界，不是实测最大并发或服务容量。C2 早期每 D 运行 16 条、随后输出增长触发压力，并不与该上界矛盾。PD 新请求还需原输入加 512 token 预留，以及运行/传输队列相关保护预算，因此不能只用“还空几个槽位”判断可接纳性。

C2 的现场证据在 `environment/C2-capacity-live-observation.json`。D 两边在尚无请求完成时分别为 16 运行+2 等待、16 运行+14 等待，支持 18/30 的实际分配；GPU2/3 平均忙碌 66.9%/98.9%，显示尾部负载不平衡。容量隔离、路由不均与 Prefill 排队同时存在，本实验没有分别估计各自贡献。

### TCP 证据和解释范围

10 Gbit/s 为每 GPU 所有流共享的发送上限和独立接收上限，全双工；不是每对 GPU 各 10 Gbit/s。CPU 校准不限速单流/共享扇出为 41.86/54.92 Gbit/s，限速为 9.56/9.27 Gbit/s；GPU PD 双对传输校准约 9.52/9.53 Gbit/s，载荷校验通过。四项 TCP 正式运行的 NVLink 计数增量为零，并验证实际 qdisc 限速值和单调接口计数。A/B/C 则保留原生互联与框架优化。D 组不是 PCIe P2P 测试。

`network-observation.csv` 的分母是网络快照间隔，包含客户端短 warmup、正式请求、序列化及监控/控制流量；接口字节不是纯 KV 负载。框架 KV 传输 latency/speed gauge 未更新，默认零不能作零延迟证据，未获得逐请求传输关键路径分解。

`routing-observations.csv` 根据有秒级时间戳的成功 POST 日志给出保守范围：D1 的 D2/D3 为 6–7 / 8–9 条，D2 为 8–9 / 6–7 条；各对总数均为 15。P 分配也有差异：D1 为 6–7 / 8–9，D2 为 5–6 / 9–10。剔除正式起点所在秒以避免把 warmup 计入，导致首条请求存在一条归属不确定性。这是观测范围，不冒充精确逐请求路由日志。

### 如何使用这些结果

本轮最清晰的 PD 不利条件是 A 的 Prefill 压力和 C2 的容量压力；D2 的不利结果主要体现在 TTFT、SLO 与 goodput，并非总输出吞吐大幅下降。B 证明“资源闲置”不能直接推出“PD 吞吐较低”。各结论仅适用于冻结的两系统配置、负载形状、短窗口及本次路由实现，不能推广为所有 PD 部署的结论。

窗口吞吐与排空吞吐必须一起看：B2 虽然 PP 排空吞吐较高，30 秒窗口内仍是 PD 较高；C 的到达窗口只有 2 秒，窗口输出接近零是负载定义的结果。到达口径联合 SLO 固定为 TTFT≤5 秒且 TPOT≤100 毫秒，不为长输入放宽。C1/C2 两系统大部分请求均错过 TTFT SLO，不能将较高吞吐表述为已达到交互延迟目标。

输入来源相对原方案有实质偏差：原拟 tokenized real text，实际继承的是按旧 trace 哈希通过 PCG64 重建的合成普通 token-ID，再生成固定长度输入。发现后未更换输入或重跑选择结果；原冻结证据保留，`environment/execution-rulings.json` 明确更正其含义。正式请求强制固定输出长度、忽略 EOS，本轮不评估语义质量。仅一次测试，不报告置信区间或统计显著性。
